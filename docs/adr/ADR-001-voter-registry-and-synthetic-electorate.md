# ADR-001: Voter registry and synthetic RWA electorate

**Status:** Accepted and implemented (2026-10-02). Email delivery is simulated; persistence, candidates and multi-post ballots remain open (see "Implementation status").
**Date:** 2026-10-02
**Deciders:** Eshaan (project owner)

## Context

VoteSphere's double-vote prevention does not hold today. The kiosk generates a fresh ring identity in the browser on every visit, the voter ID typed at the kiosk is never sent, and the server never checks that ring members belong to any electorate. Anyone can vote repeatedly, and any string is accepted as a ballot. The admin dashboard's "150 registered voters" is a hard-coded constant.

A real fix needs an **electorate**: a list of who may vote. The owner wants to start with a **synthetic roll of 50 voters modelled on an Indian RWA (Resident Welfare Association) election**.

**What RWA elections look like** (sources below; bye-laws vary by state and by society, so these are defaults, not law):

| Aspect | Common practice |
|---|---|
| Posts | President, Vice-President, General Secretary / Secretary, Treasurer, optionally Joint Secretary, plus Executive Committee members |
| Unit of voting | The household/flat: "one household, one vote", not one person, one vote |
| Who votes | The registered owner (first registered owner for joint ownership); tenants generally cannot, unless bye-laws say so |
| Barred members | Members with dues outstanding or a disputed title may lose the right to vote or stand |
| Method | Secret ballot, in person, no proxy voting |
| Process | Returning Officer (neutral, not a candidate) supervises; voter list published days ahead; 2-3 weeks' notice; nominations need a proposer and seconder |
| Tenure | Typically 2-5 years; one cited model constitution limits office-bearers to two consecutive terms |

**Constraints:** solo student project; must run on Render's free tier; persistence is deferred (SQLite resets on restart); the repo is public, so no real personal data may ever be committed; must be explainable to a college evaluator.

## Decision

1. **The roll is unit-based.** One row per flat, one vote per flat, with the registered owner as the voting member. 50 flats = 50 votes.
2. **Eligibility is derived, not stored:** `eligible_to_vote = dues_cleared AND NOT title_disputed`. Tenants and vacant-flat owners are handled by the occupancy field (owner still votes; tenant never does).
3. **Each eligible voter gets a unique, random, single-use voting code by email, issued from the admin panel** (see "Voting codes" below). The code authorises only **ring-key registration**, never ballot submission. A membership number is an identifier, never a credential: typing `PRW-009` proves nothing. The Returning Officer can still supervise the kiosk and check ID in person as a second factor.
4. **Double-voting is stopped by a frozen ring**: the ring is the set of public keys registered by checked-in members, frozen before voting opens. The server derives the ring itself and rejects client-supplied rings.
5. **The registry never links a member to a key, a key image, or a ballot** (invariants below).
6. **The starting data is synthetic**, generated by a seeded script and committed as JSON/CSV. It carries **masked** Aadhaar and phone values only (a random 4-digit prefix, then X's, for example `3713 XXXX XXXX` and `+91 7544XXXXXX`), which the Returning Officer can use as a reference when checking the ID a voter shows. It contains no full identifiers, no email, PAN, religion, or caste fields. A real deployment must never store full Aadhaar numbers; that needs legal review.

### Data model (logical; persistence choice pending)

```
Election   id, society_name, status, ring_hash, registration/voting/closing times
Unit       id, block, floor, flat_no, unit_label (unique), bhk
Member     id, membership_no (unique), unit_id (unique -> one voting member per flat),
           full_name, joint_owner_name?, aadhaar_masked, phone_masked,
           ownership, occupancy, member_since, dues_cleared, title_disputed
Credential election_id, member_id, code_hmac (unique), issued_at, redeemed_at
           unique(election_id, member_id); the plaintext code is never stored
RingMember election_id, public_key (unique)            <- NO foreign key to Member
Vote       existing columns + election_id; key_image unique per election
```

### Anonymity invariants (what the registry must never do)

1. `Member` and `Credential` never reference a public key, key image, or ballot. When a code is redeemed, the public key goes into `RingMember` in the same transaction with no link back to the code or the member.
2. The voting code is redeemed only for key registration. If ballot submission required it, code -> member -> ballot would be linkable.
3. No per-member "has voted" flag. Turnout = ballots / ring size.
4. Coarsen `castAt` (e.g. to the hour) so ballot timing cannot be correlated with check-in times.

Residual trust assumption, stated plainly: the server and Returning Officer are honest-but-curious. A malicious server that logs key-registration requests next to code redemptions could still correlate them by timing. This matches the existing design, where the server already holds the election decryption key.

### Voting codes (refinement of the owner's suggestion)

The owner's idea: stop trusting a guessable ID like `PRW-009`; give each eligible voter a unique code by email from the admin panel, enter it at the kiosk, and make it work only for the election period. Agreed, with these refinements:

| Refinement | Why |
|---|---|
| **Random, not "encoded".** Generate 100 random bits per voter, shown as 20 Crockford-base32 characters plus a check character so typos are caught, written `VS-XXXX-XXXX-XXXX-XXXX-XXXXC` (the last group is 4 data characters plus the check character). | An encoded or decodable identity can be forged or reversed once the scheme leaks. A random code carries no identity, so there is nothing to decode. |
| **Store only a hash.** Keep `HMAC-SHA256(server secret, code)`, never the code. The email is the only copy. Lookup is by hash. | A database leak yields nothing usable. Plain SHA-256 would already suffice for 100-bit random codes (unlike passwords), and the HMAC adds a cheap second layer. |
| **Single use, election-bound, time-limited.** A code can be redeemed only while the election is in the REGISTRATION phase, once; it is burned on redemption. When the admin advances the phase, unredeemed codes stop working. | Matches the owner's "short period only" requirement and stops replay or reuse after the election. (No separate expiry timestamp is stored; the phase is the clock.) |
| **Ring signature does the anonymity work.** The code is exchanged for ring-key registration only; the ballot carries just a ring signature. | Even a full database dump (member -> code hash) cannot link a member to a ballot. The admin never needs, and never sees, a name-to-ballot link. |
| **Delivery by HTTPS email API, not SMTP.** Use the Gmail API (OAuth) or a transactional-email API. | Render's free tier blocks outbound SMTP ports 25/465/587 (see sources). For the demo, send all 46 emails to one inbox using Gmail plus-addressing (`you+prw009@gmail.com`), configured by an environment variable, so no real address is committed to the public repo. |
| **Reissue = invalidate and replace.** Admin can revoke a member's unredeemed code and issue a new one; every action is logged without the code. | Handles lost or bounced emails without leaving an old live code behind. |
| **Rate-limit redemption separately**, per IP and per code, and keep it apart from the admin login limiter. | Codes are not brute-forceable at 100 bits, but the endpoint should still not be an open oracle, and a voter's failed attempts must not lock out the admin. |
| **Never log or URL-embed codes.** The voter pastes the code; no `?code=` links. | Codes in access logs, browser history or referrers would leak. |

**Threats this does not remove** (state them in the demo): whoever controls the mailbox controls the vote, so a forwarded or sold code works; email interception; phishing with fake "voting code" mails. Mitigations: keep the kiosk physically supervised so the Returning Officer can match the person to the roll (masked Aadhaar/phone can serve as the reference), and tell voters the admin will never ask for a code by reply.

**Resolved: where the voter's private key lives.** It must survive between key registration and voting (the ring must be frozen first). Deriving it from the code was considered and **rejected**: whoever issued the codes (the server or admin) could recompute every voter's key and link ballots to people, defeating the ring signature. Instead the browser generates the key at registration, keeps it in `localStorage`, and offers a downloadable backup that can be imported on another device. Anyone holding the backup can vote as that voter, and the UI says so.

**Resolved: key validation.** The server accepts only public keys that are non-identity members of the library's prime-order subgroup (`server/ring.js`), because a degenerate or out-of-group key in the ring could break verification for everyone.

### Election lifecycle

`SETUP -> ROLL_PUBLISHED -> CODES_ISSUED -> KEY_REGISTRATION -> RING_FROZEN (voting) -> CLOSED -> TALLIED`

Freezing is required because the key image appears to depend on the ring (see verification items). The UX cost is two phases at the venue: register keys during check-in, then vote after the freeze.

### Synthetic dataset (delivered with this ADR)

Generated by [server/seed/generate-voters.js](../../server/seed/generate-voters.js) with a fixed seed, so output is byte-identical on every run. Files: `server/seed/voters.synthetic.json` and `.csv`.

| Property | Value |
|---|---|
| Society | "Parijat Residency RWA (synthetic)", Blocks A and B, 5 floors x 5 flats |
| Flats / voters on roll | 50 (one voting member per flat) |
| Eligible to vote | 46 |
| Deliberately ineligible | 3 x `DUES_PENDING`, 1 x `TITLE_DISPUTED` (to exercise the eligibility rules) |
| Ownership | 38 sole, 12 joint (first registered owner votes) |
| Occupancy | 38 owner-occupied, 9 tenanted, 3 vacant |
| Flat size | 30 x 2BHK, 20 x 3BHK (equal vote regardless of size) |
| Membership numbers | `PRW-001` to `PRW-050`, earlier members first |
| Names | Fictional, drawn from 7 regional/community pools (North Indian, Punjabi, Bengali, Maharashtrian/Gujarati, South Indian, Muslim, Christian); a blocklist avoids names of well-known people; no duplicates |
| Masked Aadhaar | `aadhaar_masked`: 4 random digits (first digit 2-9, as real Aadhaar never starts with 0 or 1), then `XXXX XXXX`; unique per voter |
| Masked phone | `phone_masked`: `+91`, then 4 random digits (first digit 6-9, as Indian mobiles do), then `XXXXXX`; unique per voter |
| Not included | Caste, religion, email, PAN, any full Aadhaar or phone number |

Want all 50 eligible? Remove the `duesPending`/`titleDisputed` sets in the generator and rerun.

## Options Considered

### Option A: Unit-based roll + emailed single-use voting codes + frozen ring (chosen)
| Dimension | Assessment |
|---|---|
| Complexity | Medium (election state machine, two-phase flow) |
| Cost | Free |
| Scalability | Fine for 50; ring signature size grows linearly with ring |
| Team familiarity | Good: reuses Express/Prisma/`lrs` already in the project |

**Pros:** Matches real RWA practice. Makes double-vote prevention genuine. Admin role maps naturally to the Returning Officer. Server-derived ring also shrinks the vote payload and blocks ring spoofing.
**Cons:** Two-phase voting. Needs persistence decision. Residual honest-but-curious trust.

### Option B: Person-based roll (every adult resident votes)
| Dimension | Assessment |
|---|---|
| Complexity | Medium (household-to-person mapping, age checks) |
| Cost | Free |
| Scalability | Larger rings, slower signing |
| Team familiarity | Same |

**Pros:** Mirrors national elections.
**Cons:** Wrong for RWAs ("one household, one vote"); collects more personal data; larger ring for no benefit.

### Option C: Keep browser-generated identities and label the demo honestly
| Dimension | Assessment |
|---|---|
| Complexity | Low |
| Cost | Free |
| Scalability | n/a |
| Team familiarity | Same |

**Pros:** No new work.
**Cons:** The headline claim (double-vote prevention) stays false; an evaluator who votes twice will notice.

### Dataset source (sub-decision)
| Approach | Verdict |
|---|---|
| Seeded generator + committed JSON (chosen) | Deterministic, reviewable, no dependencies, safe in a public repo |
| Random generation at every boot | IDs and names change per restart; breaks any written test plan |
| Faker `en_IN` at runtime | Adds a dependency; can emit realistic-looking phone numbers that belong to real people |

## Trade-off Analysis

The central trade is **realism and honesty vs. UX simplicity**. Option C is free but keeps a false claim. Option A costs a real election lifecycle, but it is the only option where "a voter cannot vote twice" is true, and it mirrors how an RWA actually runs a poll (physical check-in, no proxies), which makes the demo more convincing, not less. Choosing households over persons is not a shortcut: it is the correct domain model.

## Consequences

**Easier:** real double-vote prevention; a real turnout denominator (replacing the hard-coded 150); demonstrable eligibility rules; the roll can be re-seeded on every Render restart, which softens the ephemeral-DB problem for this data.
**Harder:** election state machine; two-phase voting; ring of 50 enlarges the request. The server currently caps JSON bodies at 10 KB, so either the server derives the ring (recommended, client sends only a `ring_hash` and signature) or the limit rises.
**To revisit:** multi-post ballots and candidates (the current system supports one choice per ballot; RWA polls elect ~5 posts plus committee seats), persistence, public display of the roll (masked names?), and what a real society would need (real ID checks, legal review).

## Verification results (measured 2026-10-02 by parallel QA agents)

1. **The `lrs` key image depends on the exact ring: CONFIRMED.** `parts[0]` of the signature is `h^x` with `h = hash(ring in the order given)`. Different decoys, different order, or a different ring size each change it (and `lrs.link` returns false). So the ring must be frozen **and canonically ordered**; the one-phase rolling-registration flow is not possible with this library.
2. **Ring of 50 does not fit the 10 KB body limit: CONFIRMED.** The kiosk body is about 20.6 KB at ring 50; the largest ring that fits is 23. The server also returns the oversize error as HTTP 500 instead of 413. Decision stands: the server holds the canonical ring and the client sends only a `ring_hash` and signature. Sign/verify at ring 50 takes about 150 ms, which is fine.
3. **Browser round trip: CONFIRMED.** A ballot encrypted in a real browser decrypted correctly on the server and the admin tally matched.
4. **New finding: the key image is malleable.** The same signature with uppercase hex, or with leading zeros added to `parts[0]`, still verifies and still links, but is a different string. The server's uniqueness check compares strings, so a frozen ring alone is not enough: the key image must be canonicalised (lowercase, stripped) before the uniqueness check.
5. **Also measured:** `lrs.verify` accepts a ring of one, rings with duplicate keys, and rings padded with garbage keys, so the server must reject any ring that is not the election's registered ring.

## Implementation status

**Built and tested** (47-check API smoke test; a 46-voter scale run; a database anonymity audit; a real-browser walk through registration, freeze, voting and the race fix):
- Roll seeded at boot from the synthetic file; eligibility derived from dues/title.
- Admin issues codes (HMAC-only storage, shown once as a distribution sheet; reissue replaces an unredeemed code); phases DRAFT -> REGISTRATION -> VOTING -> CLOSED; opening voting freezes a canonical ring (minimum 3 keys); superadmin reset via `SUPERADMIN_EMAILS`.
- Server derives the ring itself; canonical signature and key-image checks; ballots must decrypt to a candidate; 15-minute time buckets; random ballot ids; public ledger plus per-ballot proofs.
- At ring 46 a vote body is about 10.1 KB, so the JSON body limit was raised to 64 KB.

**Not built / open:**
- Real email delivery (simulated; Render's free tier blocks SMTP, so an HTTPS email API would be needed).
- Persistence (SQLite resets on Render free tier; the roll is re-seeded at boot, everything else is lost).
- Candidates as their own entity and multi-post RWA ballots (ADR-002). The demo has one post (President) with four candidates drawn from the roll.
- Concurrency attack tests (parallel redemption/votes) and key-validation fuzzing were written but not run to completion; both paths rely on database unique constraints and transactions.
